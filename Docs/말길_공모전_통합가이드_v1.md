### 이 문서에서 가장 중요한 3가지

1. **공사 OpenAPI를 "실시간 호출"로 써야 합니다.** 로컬 DB 저장·캐싱 방식은 공식적으로 강력 비권고이며, 개발 기간 내 호출 이력이 없으면 심사 불이익. 이는 기획서 §9-11의 "캐싱 전략"과 정면 충돌합니다. (→ §4-1)
2. **1차 심사의 최대 배점은 "구현성 30점"입니다.** 기획서는 "대상은 적정성(30)+실용성(25)에서 딴다"고 했으나 그건 **최종심사(PT)** 기준이고, **최종심사에 가려면 1차에서 상위 3팀**에 들어야 합니다. 1차 관문은 기획이 아니라 **작동하는 완제품**입니다. (→ §6)
3. **과제 4는 두 갈래입니다.** "일회성 관광" + "**생활인구 유입**". 말길은 전자에 강하고 후자가 약합니다. 방문 ≠ 생활인구. 서비스와 기능설명서 양쪽에 생활인구 축을 명시적으로 심어야 합니다. (→ §7-2)

## 4. 개발할 때 지켜야 할 기술·설계 규칙

### 4-1. ★ OpenAPI 호출 방식 — 말길 최대 기술 리스크

**공식 입장 (FAQ 원문 요지)**

- 공사 OpenAPI는 데이터 동기화 오류 방지를 위해 **로컬 DB 저장이 아닌 실시간 호출 방식으로 활용할 것을 강력히 권고**.
- 1차 심사 자료 접수 시 **운영계정 신청 정보(신청자명, 인증키)** 를 요청하고, 이를 기반으로 **실제 API 호출 내역을 검증**.
- **로컬 DB 저장 방식으로 개발 기간 내 호출 이력이 확인되지 않으면 심사에서 불이익.**
- 부득이하게 로컬 DB를 써야 하면 **별도 신청서 작성 필요** → `tourapi@knto.or.kr` 문의.

**말길에서 왜 문제인가**

기획서 §9-11은 *"개발계정 1,000콜/일 하에서 50,670곳 수집 설계 → 캐싱 전략"* 을 전제합니다. 이는 **전형적인 로컬 DB 대량 적재 방식**이고, 심사 측이 명시적으로 경계하는 패턴입니다. 그대로 두면 데이터 활용 20점에서 감점, 최악의 경우 G3 저촉.

**권장 아키텍처 (하이브리드 2층)**

```
[1층] 사전 산출 — 파생 지표만 저장          [허용 가능]
  국문/영문 좌표 매칭, overview 어휘 등급 분석 결과
  → 저장하는 것은 원본 관광정보가 아니라 "한국어 난이도 점수"라는
    가공·파생 지표. 원본 데이터 재배포가 아님.
  → 산출 근거·산출 시점을 기능설명서에 명시.

[2층] 실시간 호출 — 화면에 뜨는 것 전부      [필수]
  사용자가 지도/목록/상세를 열 때마다
  areaBasedList2 · detailCommon2 · detailIntro2 를 실시간 호출해 렌더링
  → 개발 기간 내내 호출 로그가 쌓임 = G3 충족의 증거
```

**개발 원칙 (그대로 지킬 것)**

1. **화면에 보이는 관광정보는 반드시 실시간 호출로 그린다.** 사전 적재분을 그대로 뿌리지 않는다.
2. **8월 중 운영계정을 신청한다.** 개발계정 1,000콜/일로는 실시간 호출형 서비스 운영이 불가능. 기획서 §9-16이 지적한 대로 15101972는 **심의승인** 대상이라 일정 리스크가 있으므로 **가장 먼저 처리**.
3. **호출 이력이 개발 기간(07.27~09.21) 내내 균등하게 쌓이게 한다.** 마감 직전 몰아치기 호출은 검증에서 좋게 보이지 않음.
4. 사전 산출 파이프라인을 돌린다면 **그 자체도 공사 API 호출**이므로 이력에 포함됨 — 다만 그것"만" 있으면 안 됨.
5. 로컬 DB 비중이 커질 것 같으면 **9월 초 이전에** `tourapi@knto.or.kr`로 사전 문의해 별도 신청서 여부를 확정.

### 4-2. 위치기반서비스사업자 신고 — 말길은 직접 해당

말길은 지도 기반 서비스이므로 반드시 확인해야 합니다. 공모전 출품작·테스트 서비스라도 **법적 기준은 동일 적용**됩니다.

| 구분 | 기준 |
|---|---|
| **비신고 (제외)** | 개인위치정보를 **이용자 단말기 내부에서만** 활용하고 사업자 서버로 **전송하지 않는** 경우. 단말기에서 조회 후 서비스 내에서만 쓰이고 즉시 삭제되는 형태. 또는 개인 위치가 특정되지 않도록 **익명·가명 처리**한 경우 |
| **신고 대상** | 개인위치정보를 **사업자 서버로 전송**하는 경우. **서버 DB 저장 여부와 무관하게, 전송하는 자체만으로** 대상 |

> **말길 설계 원칙**: 사용자 GPS 좌표를 **서버로 보내지 않는다.** "내 주변 갈 수 있는 곳" 계산은 브라우저(클라이언트)에서 수행하고, 서버에는 시군구 코드 등 **비식별 단위**만 전달한다. 이 원칙 하나로 신고 의무를 회피할 수 있고, 개발 5주 안에 행정 절차를 끼워 넣지 않아도 됩니다.
>
> 주최 측은 개별 서비스에 대한 법적 확답을 주지 않으며, **위치정보지원센터**(www.lbsc.kr / 02-588-0185) 사전 검토를 강력 권장합니다. 서버 전송이 불가피한 설계로 간다면 **8월 중** 검토 요청.

### 4-3. 웹 vs 앱 — 웹을 권장

- FAQ: **"서비스 형태는 심사에 영향이 없습니다."**
- 웹: 최종 서비스 URL만 제출, 별도 승인 절차 없음.
- 앱: **9.21 마감 내 스토어 등록 및 승인 완료 필수**, 추가 기간 제공 없음. 심사 기간 고려해 미리 준비 요구.

> ⚠️ **정정 (2026-09-07)** — 위 "앱" 조건은 **참가신청 「서비스 유형」을 '앱'으로 등록할 때만** 발동합니다. **앱을 개발하는 것 자체는 제약이 아닙니다.** 1차 심사 제출 폼의 조건부 필수 구조:
>
> | 등록 유형 | 필수 요건 | 스토어 |
> |---|---|---|
> | 앱 | 안드로이드 마켓URL **또는** iOS 앱스토어URL 중 1건 이상 | 🔴 필요 |
> | 웹 | 서비스 URL | ✅ 불필요 |
> | SW·기타 | 서비스 URL **또는** 기타 자료(설치파일/구동시안/설명자료) 중 1건 이상 | ✅ 불필요 |

- → **확정 방향(D-11 해소)**: **Flutter 단일 코드베이스**로 개발하고 유형은 **「웹」**으로 등록해 **Flutter Web 빌드를 서비스 URL로 제출**합니다. 스토어 심사(구글 수일, 애플 최대 2주+ 반려 리스크)를 마감 안에 끼워 넣지 않으면서, 최종 전달 형태인 앱으로 갈 때 **재작성이 발생하지 않습니다.** 네이티브 앱 런치는 실수요 트리거 충족 후 2단계 (기획서 §1-4 · 부록 D).

### 7-2. ★ 과제 4의 "생활인구" 축이 비어 있습니다

**과제 4 원문**: *"단순 흥미 위주 일회성 관광의 한계 **및** 인구 감소 지역의 지속 가능한 **생활인구** 유입 대책 부족"*

- 말길은 **전자(일회성 → 반복 방문)** 에 대해서는 논리가 완결되어 있습니다.
- 그러나 **후자(생활인구 유입)** 는 §4-2 "3차 방문 = 인구감소지역" 한 줄뿐입니다. **방문 ≠ 생활인구.** 생활인구는 체류·정주 개념입니다.
- 공고문 [붙임]의 과제 4 예시 서비스가 **"체류형 로컬 관광 플래너"**(장기 체류 + 로컬 일자리 정보 융합, 해시태그 #워케이션 #한 달 살기 #2030청년 #로컬관광)인 것은, **심사위원이 과제 4에서 기대하는 해석의 중심이 "체류"** 임을 보여줍니다.

**조치 (택1 이상, 서비스에 실제 기능으로 구현할 것)**
1. **체류 기간 축 도입** — "3일 여행" 외에 "2주 / 한 달" 모드. 레벨이 오를수록 권장 체류가 길어지는 구조.
2. **인구감소지역 89곳 명시적 태깅** — 해당 지역 진입 시 별도 배지·보상. 정책 언어와 직결.
3. **누적 체류일 지표** — 사용자별 "내가 이 지역에 머문 총 일수"를 생활인구 기여로 환산해 표시.

→ 그리고 기능설명서 **1장 ⑥ 지정과제 선택 이유 / ⑦ 기획 방향**에서 과제 4의 **두 갈래를 각각 명시적으로 받아 적어야** 합니다. 한 갈래만 답하면 G4(과제 부합) 판단에서 약해집니다.

### 7-3. 해시태그 — 자체 도출로 확정 권장

**공식 정의**: *"선택한 지정과제의 관광 문제를 본 서비스가 얼마나 잘 해결했는지 나타낼 수 있는 대표 키워드"*
**도출 기준**: **참가팀 자율.** 공고 예시를 따라도 **가·감점 없음**. 타깃 확장·신규 기능 추가·자율 해시태그 모두 자유.
**의무**: 도출한 해시태그가 **최종 서비스 내 어떻게 연관되어 기능 구현되었는지** 기능설명서에 반드시 작성.

> **판단**: 공고 예시(#워케이션 #한 달 살기 #2030청년 #로컬관광)는 말길과 타깃이 어긋납니다(2030 청년 ≠ 외국인 한국어 학습자). 예시를 그대로 쓰면 **독창성(기획력 30점) 손해**만 보고 얻는 게 없습니다. **자체 도출하되, 과제 4와의 연결고리 1개는 남기는 것**이 안전합니다.
>
> 예: `#한국어레벨` `#실력만큼여행` `#반복방문` `#로컬한국어` + 과제 연결용 `#생활인구` 또는 `#로컬관광`

**★ 설계 순서를 뒤집으세요.** 기능설명서 2장이 *"해시태그별 연계 기능 및 흐름도"* 를 요구합니다. 즉 **해시태그 = 기능 묶음의 목차**입니다.

```
해시태그를 먼저 5개 확정
  → 각 해시태그마다 대응 기능 1~2개 정의
    → 그 기능만 5주 안에 완성 (그 외는 만들지 않음)
      → 기능설명서 2장이 자동으로 채워짐
```

이렇게 하면 **기능 범위가 자동으로 통제**되고(구현성 30점 방어), 기능설명서 작성이 개발과 동시에 끝납니다.
